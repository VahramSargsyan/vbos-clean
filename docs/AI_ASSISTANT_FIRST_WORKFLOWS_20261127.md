## 3. AI-01 — receipts and purchasing
User result: photo → inspect recognized receipt → resolve products → approve → purchase evidence + dated supplier prices. Phase A (first): offline draft-only, no DB. Phase B: persisted purchase only following approved procurement contract.
Proposed versioned draft envelope (not an API or schema decision): kind=receipt.v1, source image fingerprint where locally computed, original OCR text and per-field evidence, seller/raw taxpayer or store identifier if present, date/time/receipt number/currency, lines [rawName, normalizedCandidate, sku/barcode?, spec/diameter?, quantity, unit, unitPrice, discount?, lineTotal, materialId?, matchState], subtotal, receipt discount/tax treatment, total, optional objectId/orderId/financeTransactionId, unknowns. Preserve raw labels in Armenian/Russian/English; no guessing dates, currencies, quantities or price. Null != zero. Do not store payment card or unrelated personal data. Use decimal strings, bounded precision, explicit currency and units; compute using fixed-point server arithmetic and currency rounding/tax rules, not model arithmetic. Flag mismatch, refunds/negative lines, mixed currency, illegibility, missing seller/total or uncertain unit; no automatic approval.
- Matching: prioritize exact known barcode/SKU, canonical ID, verified alias, normalized name + type + diameter/spec + unit; ambiguous matches require selection; don't merge different diameters, thread types or pack/individual units; never create material by similarity alone. Unknown product proposal includes canonical category/unit/spec; owner explicitly confirms each new ID. Recipe vocabulary is a hint only.
- Duplicate candidates: image digest plus normalized seller/fiscal number/date and amount/currency, secondary semantic line fingerprint; rescans or missing receipt number require explicit resolution. Stable request UUID plus transactionally unique verified receipt identity where supported; do not silently drop legitimate distinct same-total receipts.
- Future canonical data requirements (logical, no DDL): supplier identity, stable material identity/aliases, purchase header + lines with immutable raw/normalized evidence and exact decimal facts, source fingerprint, unique receipt/replay constraints and audit/revision. Price history should be a view/projection of accepted purchase lines keyed by material/supplier/date/currency/unit (avoid a second writer); store conversion factor only if confirmed. Canceled/corrected purchases remain attributable; no destructive delete. Existing catalog or supplier source must be discovered and reused before defining new tables. If absent, propose additive migration in same PostgreSQL, with MIGRATION_PLAN, legacy ID mapping, rehearsal, backup/restore and owner decision; no SQL approved here.
- Purchase is not a finance posting. Optional object/order link by exact IDs verified relationship; existing transaction link only after authority/ownership, amount/currency and allocation semantics proven. No inferred expense or double count, no auto-create finance transaction; one purchase can have split payments, one payment multiple purchases (future explicit mapping decision). Phase B may leave finance link unset. Never feed purchasing records into finance totals by default.
- Acceptance future: synthetic and owner-approved redacted fixtures for all 3 languages, mixed receipt, quantity/unit, discounts/tax/rounding, same-name different spec, unknown item, repeat same/re-encoded image, two legitimate identical totals, stale reference, unauthorized, partial failure, cancellation, price history and exact readback. Every committed fixture has correct confirmed fields and arithmetic; zero duplicate purchase on replay, zero unconfirmed/unauthorized mutations, zero finance mutations. Measure raw extraction line/field accuracy, owner corrections, elapsed time and price history completeness versus manual; publish aggregate only.

## 4. AI-02 — voice/text services
User result: dictate service → canonical category/unit preview → match/edit existing or create explicitly → readback.
Draft envelope kind=service.v1: operation create/update, serviceName, category, defaultUnit, actionCode?, notes?, serviceId?, revision?, optional rate intent separate from service. Dictation e.g. 'Установка смесителя, за штуку, 7000 AMD' must distinguish price intent from service metadata. Server mapping allowed units: job,item,point,meter,square_meter,hour,day,visit,other; unknown unit or category resolved with owner; no auto merging. Search active + archived, page through matches, retain known historical distinct IDs. Explicitly choose existing ID for update; existing revision required, no model-generated IDs. Existing payload rejects price field. Call servicesCatalogSave through existing authorized flow only when writeEnabled and authority confirmed; same-origin and owner session retained.
- Rate intent is a separate preview/confirmation/receipt. If master-specific, require master UUID and chosen service ID, type, currency, unit, validFrom and existing masterPriceId/revision for update; use masterPriceSave + existing history. If estimate price, route to existing EST-PRICES-01 contract only if owner explicitly chooses its scope/card/action. A universal selling tariff per service is not found in MS2: defer to owner semantics and approved model, do not disguise as master rate. No automatic second write after service save; if second action fails report saved service ID and pending rate, never duplicate service.
- Future checks: create, update same ID, duplicate active names incl whitespace/case, historic duplicates retained, stale revision 409, missing master/archived entities, unsupported unit/category, authority LEGACY/UNAVAILABLE, same-key replay/changed payload 409, authenticated/no-CSRF/no-origin negatives, unicode voice transcription, existing history and readback.
